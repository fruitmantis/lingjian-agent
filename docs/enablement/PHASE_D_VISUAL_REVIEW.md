# Phase D 视觉与伙伴可传递视图复核

本轮为工程截图/可读性检查，**不是业务方人工验收签字**。所有截图使用合成数据，视口为 1366×768、1920×1080；长页面保存为全页图，图像高度不等于视口高度。最终采集将滚动位置重置为顶部，避免固定 App Shell 在全页截图中出现在文档中部。

## 布局与状态

自动化检查：页面无横向溢出、中心导航位于侧栏内且在视口可见，核心页面无未处理脚本异常。主流程、资源目录、详情、伙伴与项目入口保持当前浅灰/白卡/蓝色风格。

截图抽查：完整诉求（1366）、V2 draft / confirmed V1（1920）、伙伴可传递预览（1366）、失败调整保留旧版本（1366）、撤权历史（1920）、假设落库（1366）、资源目录（1920）、旧匹配详情（1366）。可追溯文件见 `artifacts/enablement-phase-d/screenshot-manifest.json`。

- 当前/确认版本在详情顶部同时展示；V2/V3 草稿不会冒充已确认 V1。
- failed revise 的详情页显示“本次处理未完成，旧版本保持不变”，下方旧方案仍存在；撤权后隐藏受影响内容并提示重新生成/联系管理员。
- 显式假设在提交前可填写，并出现在保存版本的“已接受的假设”区域；刷新后保持。
- 普通资源不可用语义由后端重新校验，不能继续返回有效跳转 URL。

**尚需产品评审的状态文案风险**：侧栏/任务列表沿用最新 Run 的“失败”标签，脱离详情可能被理解为整份方案失效；Plan active 在详情显示“进行中”，可能与执行 running 混淆。数据指针/旧版本访问的自动化测试均通过，但不能因此声称用户理解已验收。本轮未重做任务框架或改变状态模型，建议产品评审后明确“本次调整失败 / 已确认版本仍可用”和 Plan 业务状态的呈现规则。

## 伙伴可传递文本

| 评估项 | 当前观察 | 结论 |
|---|---|---|
| 发展目标 | 仅在明确允许目标外发时展示 | 权限正确；业务表达依赖输入质量 |
| 阶段目标 | 使用通用“阶段 1/2…”；不复制内部阶段标题 | 目标表达偏弱 |
| 推荐原因 | 共享元数据说明可见；模型自由推荐原因不外发 | 很难从文本单独理解选择理由 |
| 投入 | 每条资源有预计投入小时 | 可读；未汇总阶段总投入 |
| 先修条件 | 课程/实验展示元数据；未知显式保留 | 可理解，质量依赖正式数据 |
| 访问条件 | 账号、环境、语言、站点、费用可见 | 元数据 `unknown` 仍有英文表现，略机械 |
| 资源缺口 | 无可外发资源时给通用联系负责人提示 | 不能完整解释各目标的具体缺口 |
| 内部信息 | copy/preview 接口测试拒绝内部诊断、备注、ID、错误和金丝雀 | 白名单边界通过 |

结论：当前适合内部负责人核验后的受控预览/复制，**可读性不能视为真实伙伴沟通体验已经验收**。

后续建议（本轮不实施）：由产品定义受控 `partner_facing_summary`，以明确白名单、来源及撤权依赖覆盖阶段目标、推荐依据和资源缺口；审批通过前不能把模型自由文本、内部诊断、证据或备注直接开放。状态文案与外发可读性均列入最终条件项。
